Slowloris DoS Tester

HTTP/1.1 요청 헤더를 완료하지 않은 TCP 연결 여러 개를 유지하면서, 주기적으로 추가 헤더를 흘려보내는 IPv4 기반의 Slowloris 동작 실험 코드 (HTTP·HTTPS 모두 지원). 연결을 오래 붙잡아 서버의 연결·요청 처리 자원을 점유한다. 본인이 통제하는 격리 환경에서 학습·방어 검증 목적으로만 사용한다.

⚠️ 본인 소유이거나 명시적으로 허가받은 시스템에만 사용해야 합니다. 타인의 서버를 무단으로 공격하는 행위는 정보통신망법 등 관련 법률 위반이며, 그로 인한 책임은 사용자 본인에게 있습니다. 이 프로젝트는 보안 학습 및 인가된 테스트 목적으로만 제공됩니다.

동작 원리

일반적인 요청 폭탄(GET flooding)이 요청 수(rate)로 밀어붙이는 것과 달리, 이 도구는 불완전한 요청을 오래 유지하는 데 초점을 둔다.

TCP 연결을 맺고 GET / HTTP/1.1 요청을 보내되, 헤더의 끝(빈 줄 \r\n\r\n)을 일부러 보내지 않는다.
서버는 "요청 헤더가 아직 안 끝났다"고 보고 연결을 계속 열어둔다.
10초마다 의미 없는 헤더 한 줄(X-a: ...)만 흘려보내 타임아웃을 늦춘다.
이런 연결을 여러 개 유지하면, 서버 구현·설정에 따라 connection state, worker, file descriptor, 메모리, HTTP 요청 처리 자원 등을 점유할 수 있다.

특히 **연결 하나가 worker 하나를 오래 붙잡는 구조(예: Apache prefork)**에서 영향이 크다.

구현 참고 (동시성)

여러 프로세스가 각각 일정 수의 연결을 담당하도록 구현되어 있다. 다만 이 작업은 connect / send / sleep 위주의 I/O 바운드라, CPU 병렬성을 위한 멀티프로세싱이 필수는 아니다. 같은 목적을 non-blocking / 이벤트 루프(asyncio 등)로도 구현할 수 있으며, 여기서는 연결 묶음을 프로세스에 분산하는 방식을 택했을 뿐이다.

요구 사항 / 제약
Python 3.x, 외부 라이브러리 없음 (표준 라이브러리 socket, ssl, multiprocessing 등만 사용)
IPv4 전용 (socket.AF_INET) — IPv6 주소는 지원하지 않음
HTTP·HTTPS 모두 지원 — https:// 또는 443이면 ssl로 TLS 핸드셰이크 후 요청. 테스트 편의를 위해 인증서 검증은 끈 상태(CERT_NONE)이며, 격리 랩의 자체서명 인증서도 허용한다.
사용법
bash
python Slowloris_Dos.py

실행하면 대상 URL/IP와 포트를 입력받는다.

대상 URL/IP (http/https, IPv4): https://test.local
포트(기본 443): 443
http://·https://를 붙이면 프로토콜이 자동 판단된다(https → TLS, 기본 포트 443 / http → 평문, 80). host:port 형태로 포트를 직접 지정할 수도 있다.
호스트명(test.local)을 넣으면 DNS로 IP를 찾아 연결하고, 요청의 Host 헤더에는 원래 호스트명을 넣는다 (VirtualHost 대상에서도 올바른 사이트로 도달하도록). HTTPS에서는 같은 값이 SNI로도 전달된다.
중단: Ctrl+C.
프로세스 수·연결 수는 코드 상단의 processes, conns 값으로 조정한다.
출력 값 읽는 법

실행 중 1초마다 다음이 출력된다.

[*] 추적 중 소켓: 1980 | 실패 DNS:0 연결거부:412 타임아웃:0 TLS:0 기타:0
추적 중 소켓 — 서버에서 확실히 ESTABLISHED인 연결 수가 아니라, 클라이언트가 아직 살아있다고 추적 중인 소켓 수다. (TCP 특성상 상대가 연결을 닫아도 다음 I/O 전까지 즉시 알 수 없다.)
실패 유형별 카운터 — 연결 실패를 원인별로 나눠 센다. 이게 방어 관찰의 핵심이다:
연결거부가 늘어남 → 서버가 새 연결을 거부하기 시작(한도/방어 작동 가능성)
타임아웃이 늘어남 → 서버 응답 지연 또는 자원 포화
TLS가 늘어남 → TLS 핸드셰이크 단계에서 막힘
DNS → 이름 해석 문제(대상 입력 오류 등)
"추적 중 소켓"이 오르다 멈추는 것만으로 서버 한도라 단정할 수 없다. 실패 유형 분포와, 브라우저/curl 접속 지연, 서버 측 상태·로그(netstat, 액세스/에러 로그)를 함께 봐야 한다.
방어 관점 (같이 보면 좋음)
Apache: mod_reqtimeout이 헤더/바디를 너무 느리게 보내는 요청을 끊는다 — Slowloris의 직접적 대응책. MaxRequestWorkers로 동시 처리량을 관리.
nginx: 이벤트 기반이라 다수의 idle 연결을 상대적으로 효율적으로 처리한다. 다만 HTTP limit_conn은 요청 헤더를 다 읽은 연결만 카운트하므로, 헤더를 완료하지 않는 Slowloris를 곧바로 막지는 못한다 — 느린 요청 대응은 client_header_timeout 등이 담당.
방어를 껐을 때 vs 켰을 때 동작을 비교하면 방어 효과가 드러난다.

"이벤트 기반이라 안전하다"는 뜻은 아니다. 어떤 서버든 연결마다 socket·FD·커널 TCP state·메모리 비용이 있어, 상대적으로 유리할 뿐 영향을 안 받는 것은 아니다.

한계
단일 소스 IP에서 동일 대상(IP:port)으로 다수 연결을 만들면, 로컬 임시 포트(ephemeral port) 범위 등이 제한 요인이 될 수 있다.
연결 유지에 강한 서버나 적절한 timeout 방어가 설정된 서버에는 통하지 않는다(그것이 올바른 방어의 예다).
